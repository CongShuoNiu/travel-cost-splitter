# 系统架构设计文档

## 系统概述

Travel Cost Splitter 采用 **前后端分离** 的架构，包括：
- **微信小程序前端** - 用户交互和数据展示
- **Node.js 后端服务** - 业务逻辑和数据处理
- **数据库层** - 数据持久化
- **第三方服务** - OCR 识别、文件存储等

## 核心模块设计

### 用户管理模块

```
认证流程:
1. 小程序获取用户授权
2. 获取 code 和 userInfo
3. 后端调用微信 API 验证
4. 生成 JWT Token
5. 存储用户信息

权限体系:
- 出行创建者 (CREATOR)
- 出行成员 (MEMBER)
- 管理员权限 (仅创建者)
```

### 账单管理模块

```
账单生命周期:
DRAFT → PENDING_REVIEW → APPROVED → SETTLED → ARCHIVED

账单字段:
- 消费者 (Payer)
- 参与人员 (Participants)
- 金额 (Amount)
- 分摊比例 (Split Ratio)
- 类别 (Category)
- 时间 (Timestamp)
- 附件 (Attachments)
```

### 分摊计算模块

```
分摊算法:

1. 等额分摊 (Equal Split)
   每人应付 = 总金额 / 参与人数

2. 按比例分摊 (Ratio Split)
   每人应付 = 总金额 × 个人比例

3. 自定义分摊 (Custom Split)
   每人应付 = 自定义金额

4. 智能结算 (Smart Settlement)
   最小化转账次数的算法
```

### 结算管理模块

```
结算流程:
1. 生成结算清单
2. 计算各人应付/应收
3. 优化转账方案
4. 标记已结算
5. 保存结算记录

结算算法:
- 债务图构建
- 最小转账次数优化
- 循环债务消除
```

## 数据流

### 添加账单流程

```
小程序:
1. 用户输入账单信息 (或拍照)
   ▼
2. 选择参与人员
   ▼
3. 点击保存
   ▼
4. 发送 POST /trips/{id}/bills

后端:
1. 认证验证
   ▼
2. 数据校验
   ▼
3. 处理 OCR (如有图片)
   ▼
4. 保存到数据库
   ▼
5. 触发计算更新
   ▼
6. 返回响应

小程序:
1. 收到响应
   ▼
2. 更新本地缓存
   ▼
3. 刷新 UI
```

### 事件驱动设计

```
EventBus:
├── BillCreated      → 更新结算
├── BillUpdated      → 重新计算
├── BillDeleted      → 调整结算
├── SettlementMarked → 归档账单
└── UserAdded        → 重新分摊

使用:
EventBus.emit('BillCreated', billData);
EventBus.on('BillCreated', () => {
  SettlementService.recalculate();
});
```

### 缓存策略

```
Redis 缓存层:
- 用户信息缓存 (TTL: 24h)
- 出行数据缓存 (TTL: 1h)
- 结算结果缓存 (TTL: 10m)
- Session 缓存 (TTL: 7d)

缓存键设计:
user:{userId}
trip:{tripId}:summary
trip:{tripId}:bills
trip:{tripId}:settlement
```

## 安全性设计

### 认证与授权

```
认证流程:
1. 微信授权登录
2. 后端验证 code
3. 签发 JWT Token (有效期 7 天)
4. 刷新 Token (有效期 30 天)

授权检查:
- 资源所有权验证
- 角色权限检查
- 操作权限控制
```

### 数据安全

```
- 敏感字段加密 (AES)
- 密码哈希存储 (bcrypt)
- SQL 注入防护
- 请求签名验证
- 审计日志记录
```

## 性能优化

### 数据库优化

```
索引设计:
- userId + tripId (账单查询)
- tripId + createdAt (分页)
- userId + status (用户账单)

查询优化:
- N+1 查询避免 (JOIN 或批量加载)
- 分页查询 (避免全表扫描)
- 物化视图 (结算汇总)
```
